# Supabase database setup

This directory contains versioned migrations and an explicit account-approval script. No remote database is configured or changed automatically.

## Apply to your Supabase project

1. Create a Supabase project and disable public signups in **Authentication → Providers → Email**. Keep email/password login enabled. Create the intended login account through Supabase's administrative user flow and ensure it has a usable password. Do not put account passwords in SQL or environment files.
2. Open **SQL Editor** as the project administrator and execute the complete contents of `migrations/202609110001_initial_health_schema.sql` once. It is transactional and intended for a new schema. If tables already exist, review their structure first instead of overwriting them.
3. Execute `migrations/202609120001_tracker_experience.sql`, then `migrations/202609120002_attachments.sql`, then `migrations/202609120003_settings.sql`, then `migrations/202609120004_timeline.sql`, then `migrations/202609120005_providers.sql`, then `migrations/202609120006_vaccinations.sql`, then `migrations/202609120007_documents.sql`. For an existing installation, apply only migrations not yet applied.
4. Copy the existing Auth user's UUID from **Authentication → Users**. Replace the placeholder in `approve-user.sql` and run that statement. This is also how to approve existing users from the previous `ALLOWED_USER_IDS` environment setting; that setting has been removed.
5. Approval inserts two rows named **Profile 1** and **Profile 2** into `profiles`. Repeating the approval statement only re-enables access; it never resets renamed profiles or creates duplicates.
6. Set the Supabase URL and publishable key in both app environment files. Start the API and frontend, sign in, and confirm the profile selector loads both database rows.

Alternatively, use the Supabase CLI migration workflow against the intended linked project: initialize a local CLI config if needed, link the project, review pending migrations, then run `supabase db push`. The SQL Editor path does not require the CLI. Choose one migration tracking workflow; do not blindly reapply SQL already run manually.

Use the project administrator only for migrations and approvals. Runtime clients use the **publishable/anon key plus the authenticated user's token**, never a secret/service-role key.

## Ownership model

One Supabase Auth user owns one private application workspace. Its two health profiles represent people, not Auth users. A second approved login gets a separate, isolated workspace and its own pair of profiles. Sharing a workspace across login accounts would require a future membership model; it is deliberately not implied by approving another account.

`app_users` is the database-managed approval list. Authenticated users can read only their own enabled membership and cannot insert, update, or delete membership rows. Disable access without deleting data:

```sql
update public.app_users
set enabled = false
where user_id = 'REPLACE_WITH_AUTH_USER_UUID'::uuid;
```

Both Express and all private-table RLS policies check membership. Disabling a user blocks subsequent database/API reads and writes even while their JWT is unexpired. Already downloaded information cannot be recalled. Deleting an Auth user or their membership row cascades deletion of all of their workspace data; use `enabled = false` to revoke access without deleting records.

## Tables and integrity

| Table               | Purpose                                                                |
| ------------------- | ---------------------------------------------------------------------- |
| `app_users`         | Administrator-managed account approval and enable/disable state        |
| `profiles`          | UUID, owner, name, optional avatar object path, creation timestamp     |
| `health_events`     | All requested event fields, owning profile, creation/update timestamps |
| `categories`        | Workspace-owned category names                                         |
| `tags`              | Workspace-owned tag names                                              |
| `health_event_tags` | Unique event/tag associations within one workspace                     |

Every data table includes `owner_id` in addition to the requested fields. It defaults to `auth.uid()` and is validated by RLS on every insert and update. UUIDs are generated by PostgreSQL. Names, event types, and titles cannot be blank. Tag/category names are unique within a workspace after trimming and case folding.

Event dates use `timestamptz`: send ISO timestamps with offsets; PostgreSQL preserves the instant, and the UI displays local time. `end_date` must not precede `event_date`. Optional clinical detail fields are nullable text. `description` defaults to an empty string. A trigger maintains `updated_at` on every event update.

Composite foreign keys carry `(owner_id, id)` through profile/event/tag relationships, preventing cross-owner links even when valid foreign UUIDs are known. Profile deletion cascades to events and their tag links; event or tag deletion removes the corresponding links. Events have one nullable category linked through a same-owner composite foreign key; `event_type` remains separate text. Event and tag updates use an atomic transaction. Avatars are reserved private object paths, and attachments use a separate private Storage bucket.

Indexes support owner filtering, profile calendars, event dates, event types, unique labels, reverse tag lookup, and foreign-key cascades.

## RLS and security tests

```sh
npm run test:db
```

The test runs all migrations in PGlite (embedded PostgreSQL), with synthetic Supabase `auth.users`, `auth.uid()`, `anon`, and `authenticated` fixtures. It executes real RLS policies, foreign keys, grants, and triggers. It checks two owners, anonymous and unapproved callers, account revocation, ownership spoofing, cross-owner links, update timestamps, validation, and delete cascades. It also checks category/tag ownership, atomic rollback, filtered search, and dashboard isolation. Every fixture is in an isolated in-memory database; no real health data is used.

These tests do not emulate Supabase Auth's HTTP service or deployment settings. After applying the migration, verify real sign-in, refresh, sign-out, and expired-token behavior in your configured project. To verify production isolation, create two disposable approved test accounts, use their JWTs with the Data API, and confirm that each sees only its own data. Never use a service-role key for RLS validation because it bypasses RLS.

The policies follow [Supabase RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security). Cookie handling follows [Supabase SSR guidance](https://supabase.com/docs/guides/auth/server-side/creating-a-client?framework=nextjs).

## Attachment storage

`202609120002_attachments.sql` creates `attachments` with owner and event foreign keys, immutable metadata, size/type constraints, and an indexed event lookup. It also creates the private `health-attachments` bucket and SELECT/INSERT/DELETE Storage policies; object updates/overwrites are not permitted. Approved owners can upload only to an exact metadata-reserved path and can read/delete only their own files. The Storage INSERT policy validates reported object size and MIME type against metadata; bucket restrictions enforce the size/type allowlist independently.

Use the app/API to delete attachments before events. Event deletion is restricted while metadata remains; the API removes each object through the Storage API and then deletes metadata. Never delete `storage.objects` rows directly, since that does not delete the stored bytes. Account removal and administrative database changes need a Storage cleanup step first. See the root README for retry and concurrency limitations.

The attachment test supplies a minimal Storage schema in PGlite and executes the actual policies. It verifies SQL enforcement, not the hosted Storage HTTP service or underlying object deletion. Apply migrations and test upload, authenticated download, deletion, and denial under a second account in your Supabase deployment.

## Settings migration

`202609120003_settings.sql` adds the private `profile-avatars` bucket, image/size restrictions, and owner-profile path policies. Existing profile RLS governs photo operations and renaming. Removing a category sets only `health_events.category_id` to null; health events remain intact. Tags retain their existing link-only delete cascade. The migration adds a NOT VALID path constraint so legacy avatar values do not prevent installation; review any legacy values before editing those profiles. Runtime writes must use the new bucket's profile-specific paths or null.

## Timeline migration

`202609120004_timeline.sql` adds an indexed attachment date lookup and the authenticated `health_timeline` function. It combines event start dates with attachment upload dates, excludes reservations without Storage objects, and returns bounded summaries and labels. All reads run as the authenticated caller under RLS. Existing data needs no backfill. Tests cover document visibility, year boundaries, filtering, pagination, incomplete uploads, and cross-owner isolation.

## Provider migration

`202609120005_providers.sql` creates owner-scoped healthcare providers, adds an indexed optional provider foreign key to events, and updates the security-invoker event save/read/filter functions. Provider deletion nulls only the reference; clinical details and recorded doctor text remain. Existing free-text doctor names are left unchanged and unlinked. Tests check cross-owner linking denial, event persistence after provider removal, saved-provider serialization, and timeline filtering.

## Vaccination migration

`202609120006_vaccinations.sql` adds optional disease and next-dose fields to health events, includes them in event summaries, and extends the dashboard result with at most three future manually entered dose dates per profile. It contains no recommendation intervals or clinical decision logic. Existing event, provider, attachment, and RLS policies continue to govern each vaccination record.

## Documents migration

`202609120007_documents.sql` adds attachment category and description fields, defaults existing files to `other`, and adds the authenticated `search_health_documents` function. It filters completed uploads by profile, MIME group, event, document category, upload date, event tags, and literal filename/description text. The function is a security invoker and relies on the existing attachment, health-event, label, membership, and private Storage RLS policies. Pagination is capped at 100 rows per request.

## Health episodes migration

Apply `202609120008_episodes.sql` after Documents. It creates `health_episodes`, `health_episode_events`, ownership policies, profile-consistent foreign keys, atomic save/read functions, and extends `health_timeline` with episode entries. Existing event data needs no backfill. Episode deletion removes links only. Database tests verify isolation, profile consistency, rollback, timeline inclusion, and preservation of events.
